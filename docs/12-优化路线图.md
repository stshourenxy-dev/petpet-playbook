## 第一部分 · 第三轮新发现

### N-1 · 切换宠物会永久泄漏纹理显存（P0-1 修复引入的回归）

`viewer/src/main.ts:272`

```ts
pet = data
textures = {}          // ← 只丢引用，不释放 GPU 资源
```

全文件只有一处 `.destroy()`（`main.ts:340` 的 `sprite.destroy()`），**没有任何 `Texture.destroy()` 或 `PIXI.Assets.unload()`**。

PixiJS v8 里 `Texture` / `TextureSource` 是 GPU 资源，丢掉 JS 引用**不会**释放显存——何况 `PIXI.Assets` 的缓存还持有强引用，GC 根本够不着。

**用真实素材量一下**（`examples/redshao-demo/`）：

| 精灵表 | 尺寸 | 解码后显存 |
|--------|------|-----------|
| `knead_sheet.png` | 6144×288 | 6.8 MB |
| `sleep_sprite.png` | 6144×512 | 12.0 MB |

demo 只有 2 个动作就 **18.8 MB**。而 06-参数详解 §6 记录的标准规格是 1024×1024 / 1024×576 单帧、12 帧横排 → 单表 12288×1024 = **48 MB**，12288×576 = **27 MB**。一只 8 动作的完整宠物按均值 30 MB 算，**一次 `loadPet` ≈ 240 MB 显存**。

在两只宠物间来回切 5 次 = 10 次 `loadPet` = **约 2.4 GB 显存不可回收**。而托盘的「🐕 切换宠物」就是给人反复点的。

**修**：`loadPet` 开头先释放旧资源，且必须在 `textures = {}` 之前：

```ts
// 释放上一只宠物的 GPU 资源（destroy(true) 连 TextureSource 一起销毁）
if (sprite) { sprite.destroy(); sprite = null }
for (const frames of Object.values(textures)) {
  frames.forEach(t => t.destroy(true))
}
await Promise.all(loadedAssetKeys.map(k => PIXI.Assets.unload(k)))
loadedAssetKeys = []
textures = {}
```

注意顺序：当前 `sprite` 仍在引用旧纹理，必须先 destroy sprite。`Assets.unload` 需要记住加载时用的 key——这一点和 N-3 直接相关（见下）。

**验证**：切换宠物 10 次，用 Chrome DevTools 的 Memory 面板或 `PIXI.Assets.cache` 的条目数确认不再单调增长。

### N-2 · 首帧被「全部动作加载完」阻塞，期间窗口完全不可见

`viewer/src/main.ts:278-308`

```ts
await Promise.all(
  Object.entries(pet.actions).map(async ([name, act]) => { … })   // 全部 8 个动作
)
const firstAction = Object.keys(pet.actions)[0] || 'idle'
playAction(firstAction, 'init')     // ← 全部加载完才画第一帧
```

窗口是 `transparent: true` + `frame: false`，在第一帧画出来之前，用户桌面上**什么都没有**——和第一轮 P0-2 修复前的观感一模一样，只不过这次原因是「还在加载」而非「加载失败」。

一只 8 动作的宠物要先把 ~16 MB 的 PNG 全读完、全转 base64、全过 IPC、全解码上传 GPU，才会出现。冷启动（含首次 GPU 上传）这段空窗期是秒级的。

**修**：先加载首个动作 → 立刻 `playAction` → 其余后台补。改动很小：

```ts
const names = Object.keys(pet.actions)
await loadAction(names[0])          // 只等第一个
playAction(names[0], 'init')        // 立刻有画面
void Promise.all(names.slice(1).map(loadAction))   // 其余不阻塞
```

配套：`requestAction` 已经有 `if (!textures[name]) return` 守卫（`main.ts` 仲裁层），后台加载期间点到未就绪的动作会被安全忽略——**但会静默无反应**。建议加载中给个气泡「还在准备这个动作…」，或按 11 §2.2 的 schema 校验结果预先禁用未就绪的菜单项。

### N-3 · 资产走 base64 dataURL 通道：主进程同步读盘 + 缓存键是几 MB 的字符串

`viewer/main.js:271`

```js
return { dataUrl: `data:${mime};base64,${buf.toString('base64')}` }
```

三个叠加的代价：

1. **base64 膨胀 33%**。demo 的 4.27 MB 磁盘资产 → 5.7 MB 字符串。8 动作的完整宠物 ≈ 16 MB → **21 MB 字符串**，每次 `loadPet` 全量过一遍 IPC（结构化克隆需序列化+反序列化两次拷贝）。
2. **`readFileSync` 在主进程**。主进程同时负责托盘、原生菜单、提醒调度、日记窗口 IPC——加载期间这些全部卡住。
3. **`PIXI.Assets.load(res.dataUrl)` 的缓存键就是那个几 MB 的 dataURL 字符串**。这既让 N-1 的 `Assets.unload` 难写（得原样留着 key），又意味着 Assets 缓存本身在按 MB 级字符串做索引。

**修（一并解决 N-1 的 key 问题）**：注册自定义协议，让渲染层用短 URL 引用资产：

```js
// 主进程
protocol.handle('petpet', (req) => {
  const { host, pathname } = new URL(req.url)         // petpet://<petId>/<rel>
  const full = path.join(PETS_ROOT, host, decodeURIComponent(pathname))
  const rel = path.relative(PETS_ROOT, full)
  if (rel.startsWith('..') || path.isAbsolute(rel)) return new Response(null, { status: 403 })
  return net.fetch(pathToFileURL(full).toString())     // 流式，不进主进程内存
})
```

渲染层 `PIXI.Assets.load('petpet://redshao-demo/knead/knead_sheet.png')`，`index.html` 的 CSP 加 `img-src 'self' data: blob: petpet:`。

收益：零 base64、零主进程内存驻留、缓存键变成稳定短字符串（N-1 的 unload 直接可写）、路径边界检查集中在一处（复用二轮 D-2 已修好的 `path.relative` 写法）。

**注意**：`protocol.handle` 需要在 `app.whenReady()` 前用 `protocol.registerSchemesAsPrivileged` 注册 scheme，否则 CSP 和 fetch 语义会不对。

### N-4 · 方法论的两件核心产物没有机器可读形式 —— 这是定位级的

这是本轮**最值得做**的一条，因为它命中的是仓库的立身之本而非实现细节。

README 的定位是「从真实宠物照片到桌宠的完整生产管线」，而这条管线的前两步——**16 字段特征收集表**（docs/01 §3）和**五要素提示词模板**（docs/02 §1）——目前**只以 markdown 表格的形式存在**。

仓库里所有 `.json` / `.csv` / `.yaml` 文件的完整清单：

```
pyproject.toml            viewer/package.json      viewer/tsconfig.json
viewer/package-lock.json  examples/redshao-demo/pet.json
```

**没有任何一个特征表模板、提示词模板或画像文件。**

用户要走完流程，必须：手抄 docs/01 的 16 行表格 → 手动对照 docs/02 §2 的翻译规则表把每个字段拼成提示词 → 生成 → 再手写 pet.json。**三次手工转录，每次都能出错，且没有任何一步可校验。**

而 docs/02 §2 那张「逐字段翻译规则表」本身**就是一份生成器的规格说明**：

| 画像层字段 | 提示词翻译 |
|-----------|-----------|
| 品种 | 「皮克斯3D卡通风格的{品种}」 |
| 长宽高比例 | 「体长体高比约 {长:高}」 |
| 腿长比 | 「腿长比例约 {比}」 |

规则已经写死了，只差有人把它变成代码。

**修**（三个小文件，闭合整条链路）：

1. `templates/pet-profile.example.json` —— 16 字段的填空模板，字段名与 docs/01 §3 一一对应
2. `schema/pet-profile.schema.json` —— 校验它（枚举值、必填、取值范围）
3. `pipeline/gen_prompt.py --profile mypet.json --action stretch` —— 按 docs/02 §2 的规则表输出五要素提示词，含「否定词禁用」「动词链」「幅度词显式」三条铁律的自动提醒

这样管线从 4 个脚本变成 5 个，**覆盖范围从「④抽帧–⑧拼表」前移到「①特征采集–⑧拼表」**，README 全景图里 ①②那两个「一次性」步骤才真正有工具支撑。

> 顺带：这一条和 11 §2.2 的 `pet.schema.json` 是同一件事的两端——一个校验**输入**（画像），一个校验**输出**（宠物包）。合起来做只需要引入一次 JSON Schema 依赖。见下面的「合流」。

### N-5 · 仓库二进制体积

`examples/redshao-demo/` 新增了 4.27 MB 精灵表（`knead_sheet.png` 2.83 MB + `sleep_sprite.png` 1.44 MB）。加上原有 `examples/` 4.6 MB 与 `assets/` 1 MB，当前 pack 约 25.5 MB。

这个取舍**本身是对的**——「可运行的最小示例」解决的是首次体验问题，价值远大于体积成本。但有两点值得现在就定下来，因为 git 历史不可逆：

1. **精灵表建议转 WebP 无损**。08-接口协议 §V2 规格自己写的就是 `spritesheet.webp（无损）`，而 demo 用的是 PNG。同内容 WebP 无损通常小 20–30%，且 `main.js` 的 MIME 表已经支持 `.webp`。
2. **定一条「仓库内示例素材上限」**并写进 CONTRIBUTING。否则第三方按 11 §3.2 提交宠物包收录时，很容易有人直接把 50 MB 素材塞进 PR。收录页应该只放**链接**，不放素材。
