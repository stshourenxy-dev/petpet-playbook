## 2. 立即做

### 2.1 行为转移链：把已声明的 `transitions` 实现出来 —— 参考 Shimeji `NextBehaviorList`

**这是本轮最高性价比的一条：字段已经在类型里了，只是没人用。**

`viewer/src/main.ts:21`

```ts
interface PetActionSpec {
  weight?: number
  transitions?: Record<string, number>   // ← 声明了，全项目零引用
}
```

**现状的问题**：`startRandomBehavior` 只读 `weight`，且只在 `currentAction === 'idle'` 时触发。所以行为图永远是 `idle → X → idle` 的星形，任意两个非 idle 动作之间没有关系。表现出来就是：睡觉播完回待机，下一轮可能直接奔跑——缺少「刚睡醒会先伸懒腰」这类**因果感**。而 06-参数详解 §4 把 `weight` 定义成「宠物性格的量化」，星形结构其实表达不了性格，只能表达偏好频次。

**Shimeji 的做法**（`conf/behaviors.xml`）：

```xml
<Behavior Name="SitDown" Frequency="200">
    <NextBehaviorList Add="true">
        <BehaviorReference Name="SitWhileDanglingLegs" Frequency="100"/>
        <BehaviorReference Name="LieDown"             Frequency="100"/>
    </NextBehaviorList>
</Behavior>

<Behavior Name="LieDown" Frequency="0">
    <NextBehaviorList Add="false">
        <BehaviorReference Name="SitDown" Frequency="100"/>
    </NextBehaviorList>
</Behavior>
```

三个可借鉴的设计点：

1. **每个行为自带「下一步候选表 + 各自权重」** —— 即一条马尔可夫转移链，而不是全局权重池。这正是 `transitions: Record<string, number>` 的语义。
2. **`Frequency="0"` = 不参与自发抽取**，只能由转移链或事件进入。`LieDown` 就是这样：狗不会凭空躺下，只会从「坐下」转过去。viewer 现在用 `weight ?? 0` 过滤（`main.ts:524`），语义已经吻合，**差的只是转移链这一半**。
3. **`Add="true|false"`** —— 候选表是「追加到全局池」还是「替换全局池」。这是个很巧的开关：`Add=false` 表达强约束（躺下之后**只能**坐起来），`Add=true` 表达倾向。

**落到 viewer 的改法**（约 10 行，无 schema 变更）：

```ts
// startRandomBehavior 内，替换现有的候选池构造
const cur = pet.actions[currentAction]
const pool = cur?.transitions
  ? Object.entries(cur.transitions)                     // 有转移链 → 用它
  : Object.entries(pet.actions).map(([n, a]) => [n, a.weight ?? 0])  // 否则退回全局 weight
const candidates = pool.filter(([n, w]) => textures[n] && n !== currentAction && w > 0)
```

同时把「只在 idle 时触发」的守卫放宽：**有 `transitions` 的动作允许自发转移**，没有的保持现状。这样老宠物包行为完全不变（纯增量），新宠物包可以写：

```json
"sleep":   { "transitions": { "stretch": 80, "idle": 20 } },
"stretch": { "transitions": { "idle": 100 } },
"run":     { "transitions": { "idle": 70, "sniff": 30 } }
```

红苕「睡醒先伸懒腰」这种性格，就从注释变成了数据。

**成本**：约 1 小时（含 state-priority 的仲裁交互测试）。**风险**：低——纯 fallback 设计，`transitions` 缺失时行为逐字节不变。**验证**：给 `sleep` 配一条 `transitions` 后连续观察 10 分钟，确认转移按权重发生且不与 `shouldPlay` 仲裁冲突。

> 顺带清掉一处第一轮的遗留：`state-priority.ts` 的 `ACTION_PRIORITY.remind = 7` 是装饰性的（`remind` 从来不是动作名）。转移链落地时一并把它改成真实动作名或删掉。

### 2.2 宠物包 JSON Schema + 校验器 —— 参考 openpets / DyberPet

**这一条同时解决三个已知问题**，是本轮第二高性价比：

| 已知问题 | 出处 | Schema 如何解决 |
|---------|------|----------------|
| 加载失败静默，首次运行空白窗口 | 一轮 P0-2 | 校验失败时有**结构化**错误（哪个字段、哪一行），能直接显示给用户 |
| 文档默认值与代码不符（`weight` 文档说 10、代码是 0；`fps` 文档 5、代码 4） | 二轮 D-6/D-7 | Schema 成为**唯一真相源**，文档从它生成，不会再漂 |
| `frameWidth`/`cellWidth` 同时缺失 → 切片得 NaN，精灵静默不可见 | 二轮 D-8 | `required` + `minimum` 直接拦在加载前 |

**openpets 的做法**：`packages/cli/schemas/openpets.plugin.schema.json` 定义插件清单，配 `check-plugin-sdk-conformance.ts` 做一致性检查，并把 CLI 单独拆成一个 package。

**DyberPet 的做法**（更贴近本仓库的受众——素材作者而非程序员）：art_dev.md 明确写着

> 「开发过程中的测试可以使用 `系统` 内对应模组的自动添加功能，**程序会检查模组文件夹并给出潜在的错误提示**」

即校验器**内置在 App 里**，素材作者不需要装 Node 或跑命令行。这个取舍对本仓库尤其对——目标用户是「想给自家狗做桌宠的人」，不一定是开发者。

**落到本仓库的改法**（三处复用同一份 schema）：

1. 新增 `schema/pet.schema.json`（JSON Schema draft 2020-12），把 08-接口协议 §2 的表格**机器化**，默认值写进 `default` 字段
2. 新增 `pipeline/validate_pet.py`：`python pipeline/validate_pet.py ~/.petpet/pets/mypet/` → 逐条报错。这是管线的**第 5 个脚本**，正好补上「⑨ 部署」那一步目前没有任何校验的空白
3. `viewer` 加载时校验，失败走已经做好的 `showFatal()`（一轮 P0-2 的修复成果），把字段级错误直接显示在窗口里
4. CI 加一步：拿 `examples/` 生成的宠物包跑 `validate_pet.py`，防止 schema 与文档再次漂移

**成本**：schema 约 2 小时，validator 约 2 小时。**风险**：低。**注意**：schema 一旦发布就是兼容性承诺——建议先标 `"version": 1` 并在 08 里写明演进策略（这一点 docs/10 §P2 对主题包的判断同样适用）。

### 2.3 把硬编码文案下沉进宠物包 —— 参考 DyberPet `bubble_conf.json` / `note/`

一轮 P0-3 修掉了「红苕」这个名字，但**文案本身还是硬编码的**：

`viewer/src/main.ts:90`

```ts
const BUBBLE_TEXTS = ['汪！', '摸摸我～', '今天也要开心哦！', '饿了…有吃的吗？', '(*^▽^*)']
```

做一只猫，它会「汪」。做一只鹦鹉，它还是「汪」。名字模板化了，**物种没有**。

**DyberPet 的宠物包结构**把这类内容全部下沉：

```
桌宠名字/
├── act_conf.json      # 动作参数
├── pet_conf.json      # 桌宠属性
├── msg_conf.json      # 对话文本
└── note/
    ├── note.json         # 通知图标 / 音频
    ├── bubble_conf.json  # 各类型气泡的图标、音频、文字
    ├── random_chat.wav   # 点击时随机播放的语音（可加任意多条）
    └── icon.png
```

**落到 viewer 的改法**（配合 2.2 的 schema 一起做）：

```jsonc
{
  "bubbles": ["汪！", "摸摸我～", "…"],          // 替代 BUBBLE_TEXTS
  "actions": {
    "sleep": {
      "diary": { "mood": "安逸", "text": "{name}蜷成一团睡着了，呼噜声轻轻的。" },
      "label": "睡觉"                              // 顺带解掉二轮 P2-7：自定义动作在菜单里显示原始英文 key
    }
  }
}
```

代码侧的 `ACTIVITY_TEXTS` / `ACTION_LABELS` / `BUBBLE_TEXTS` 三张硬编码表全部降级为**内置默认值**（宠物包没写时才用）。

**顺带**：DyberPet 的 `random_chat.wav` 提示了一个本仓库完全没有的维度——**声音**。00-设计缘起 的脑洞清单里可以补一条评估（叫声/环境音是桌宠沉浸感的重要一环，但也是最容易变成骚扰的功能，值得单独做取舍决策）。

**成本**：约 2 小时。**风险**：低（全部走默认值 fallback）。

## 3. 值得做

### 3.1 三平台真发布 —— 参考 BongoCat

BongoCat（22449 star，Vue + Tauri）的 README 顶部直接挂 Windows / macOS / Linux 三个 release badge，加一个总下载量 badge。

对照本仓库：09-双端适配 诚实标注了「Windows 未验证」——这个诚实是对的，但**CI 三个 job 是 ubuntu×2 + windows×1，唯一被实测过的 macOS 一次都不构建**（二轮 E-3）。也就是说，唯一有把握的平台反而没有构建保障。

可借鉴的**不是换 Tauri**（Electron 已经跑通，切换成本远大于收益，属于「不做」），而是三件工程实践：

1. CI 补 `macos-latest` 的 build job（成本极低，且是唯一实测平台）
2. tag 触发的 release workflow，产物自动挂到 Releases
3. README 顶部挂平台 badge + 下载量 badge——这是**降低陌生用户门槛**最直接的一步，比任何文档都有效

> 二轮 D-5 提到 CI 产物路径已修好（`viewer/release/*.exe`），但 `.gitignore` 至今没有 `release/`——做 release workflow 之前先补上。

### 3.2 生态入口：宠物包收录页 —— 参考 DyberPet `docs/collection.md` / openpets `plugins/community/`

DyberPet 有一个 `docs/collection.md` 浏览角色与模组；openpets 直接在仓库里开 `plugins/community/` 收社区插件（每个带自己的 README + locales）。

本仓库的 `examples/` 目前只有作者自己的两只狗（红苕、包包）。README 强调「已在两个品种上验证」——**第三个品种只能靠别人贡献**，但现在没有任何收录入口，别人做完了不知道往哪放。

可做：`docs/宠物包收录.md`，一个表格（宠物名 / 品种 / 作者 / 仓库或下载链接 / 动作数），接受 PR 提交。零成本，且直接服务于「方法论可复现」这个核心主张——**别人做成了，才证明方法论有效**。

### 3.3 至少加一份英文 README —— 参考 openpets

openpets 维护 7 种语言的 README（en / ja / ko / zh-Hans / zh-Hant / pt-BR / es-419）。BongoCat 也是中英双语。

本仓库全中文。方法论本身（照片 → 特征表 → 提示词 → 管线 → 精灵表）是**语言无关**的，中文只是表达介质。一份英文 README（哪怕只是全景图 + 快速开始 + 文档索引）就能打开完全不同的受众面。

配合二轮 C-2（全仓库指向 `.md` 的链接数为 0）一起做——两者都是「文档可达性」问题。

### 3.4 为自己的项目写一份 Claude Code Skill —— 参考 openpets `skills/`

openpets 仓库里有 `skills/openpets/SKILL.md` + `references/{commands,config-files,integrations,source-docs}.md`——让 AI 助手能正确地为这个项目工作。

这一条对本仓库特别贴：受众高度重合（用 AI 生成宠物素材的人，大概率也在用 AI 写代码），而且 `docs/审查清单.md` 已经证明了本仓库有沉淀「可复用方法」的习惯。一份 `skills/petpet/SKILL.md` 教 AI 怎么读 08-接口协议、怎么跑管线、怎么排查黑屏，成本很低。

## 4. 明确不借鉴

沿用 docs/10 §3.4 的体例，以下属于他人领域逻辑或与本仓库定位冲突，**整体排除**：

| 项目 | 不借鉴的部分 | 理由 |
|------|-------------|------|
| BongoCat | Tauri 技术栈迁移 | Electron 已跑通且 04-架构设计 有完整论证；迁移成本远大于收益 |
| DyberPet | 养成 / 任务 / 商店 / 物品系统 | 那是「养成游戏」定位，本仓库是「真实宠物的替身」——03-需求梳理 已明确这条边界 |
| openpets | 沙箱插件 SDK（权限/配额/存储/调度） | 08-接口协议 的定位是「数据可定制」，不是「代码可插拔」。引入插件运行时等于引入完整的安全模型，是数量级的复杂度跃升 |
| Shimeji | `Condition` 环境感知（贴墙/爬窗沿/掉落物理） | 有意思但属于「屏幕物理」领域；本仓库的宠物是「陪着你」不是「在屏幕上爬」。00-设计缘起 的脑洞清单可以记一笔，但不做 |
| 全部 AI 女友 / 陪聊类项目 | LLM 对话层 | 03-需求梳理 已把定位从「AI 对话」区分开——本仓库的价值在生产端 |
