# 对抗性 UI/UX 审查清单

> 用途：发布或大改动前，用「陌生人视角」对客户端代码做一次对抗性走查。
> 核心思想：**开发过程是快乐路径优化——测试者永远走"作者走过的路"。对抗性审查专走坏路**：换个宠物名、删掉数据文件、输错输入、缩到最小窗口，看系统如何表现。
> 本文档是从一次真实审查（37 项问题，5 阻断 / 8 严重 / 9 中等 / 7 打磨 / 8 文档偏差）中提炼出的可复用清单。

---

## 0. 审查视角与前提

- **视角**：假设审查者是刚 clone 仓库、想给自己的宠物做桌宠的陌生人，而不是作者本人。
- **方法**：源码逐行走查 + 关键路径实测 + grep 全量扫描。实测优先于推断（"未实机运行"的结论要明确标注）。
- **基线**：记录审查基线 commit，修复后按基线复验，避免"审的是旧版、修的是新版"。
- **对抗性**：对每一条"作者不会遇到"的路径穷追不舍——那不是边缘情况，是陌生用户的第一体验。

## 1. 分级标准

| 级别 | 含义 | 典型场景 |
|------|------|---------|
| **P0 阻断** | 新用户拿不到任何价值，或功能实际不可用 | 首次运行空白窗口、核心功能点不动、加载失败无提示 |
| **P1 严重** | 产生错误结果 / 静默数据丢失 / 承诺的功能不存在 | 时间解析错、提醒丢失、文档说有的功能代码里没有 |
| **P2 中等** | 可用性与可访问性缺陷 | 对比度不足、键盘不可用、不可复制、布局裁切 |
| **P3 打磨** | 死代码、抖动、一致性 | 无调用者的函数、遗留样式、交互竞态 |
| **D 文档偏差** | 文档/配置与代码事实不符 | README 承诺与实现冲突、文档参数默认值错误 |

## 2. 检查维度（按问题产生机制分组）

### A. 身份假设——"我的机器上成立"不等于"所有人机器上成立"

- [ ] 是否有硬编码的资源名/宠物名/路径（grep 项目名、宠物名、用户目录）
- [ ] `list`/`discover` 类 API 是否真的被调用，还是写了但主路径走硬编码
- [ ] 数据文件不存在 / 解析失败时，是静默返回还是可见报错
- [ ] 文案是否模板化（名字、路径、数量都应是变量注入）

### B. 错误路径——happy path 之外发生了什么

- [ ] 用户输入格式错误时，是否有**回显**（把解析结果读给用户，而不是只说"好哦"）
- [ ] 异步失败是否被吞掉（catch 里只 console.error = 对用户静默）
- [ ] 窗口隐藏 / 未聚焦时，通知是否仍可达（系统通知兜底）
- [ ] 多条事件同时到达：是覆盖还是堆叠（队列）
- [ ] 时间/正则解析：对每种输入句式做实测（带分钟、中文数字、半、跨度）

### C. 迭代残留——改 A 忘 B

- [ ] grep 全仓库找无调用者的函数、无消费者的事件、无 CSS 响应的 data 属性
- [ ] 同一份数据是否存在于多处（label 表、文案表）且一致
- [ ] 功能入口删了，底层 IPC / 写盘路径是否也删了（"幽灵功能"：会改用户数据但屏幕上无变化）
- [ ] 配置改了（输出目录、图标路径），引用它的 workflow / 文档是否同步

### D. 边界与量纲

- [ ] 固定 px 布局在最小窗口下是否裁切（算一遍盒模型：padding 是否计入宽度）
- [ ] 定时器频率 × 每次副作用 × 存储上限：量纲后果是否算过（例：12s/条 × 100 条 = 20 分钟轮换）
- [ ] 多显示器：窗口定位是否用了正确的 display（getDisplayNearestPoint 而非 Primary）
- [ ] 垂直/水平边界是否都有钳制
- [ ] 数字解析：默认值用 `?? 0` 还是 `|| 4`（0 会被吞）、`\d` 是否在普通字符串里被吞转义

### E. 可访问性（WCAG）

- [ ] 正文对比度 ≥ 4.5:1（半透明背景按 alpha 合成到**最有利**底色计算，那是上界）
- [ ] 深色模式：硬编码的浅色值是否漏网（按钮底、边框、焦点环）
- [ ] 键盘：Esc/Cmd+W 关闭、focus-visible 样式、Tab 可达
- [ ] `user-select: none` 是否误伤内容（日记/列表应可复制）
- [ ] `prefers-reduced-motion` 降级；隐藏时动画/定时器是否暂停（耗电）
- [ ] canvas 有 role/aria-label；动态内容有 aria-live；列表有语义角色

### F. 文档一致性

- [ ] README 承诺的路径/命令/占位符与代码一致（`<宠物名>` 是不是假占位符）
- [ ] docs 里的默认值（fps/weight/字段表）与代码 `??`/`||` 的实际默认一致
- [ ] docs 描述的架构（现状表）与代码事实一致——**写文档时查代码，不凭记忆**
- [ ] 配置项（打包图标/输出目录）引用的文件真实存在

## 3. 输出格式

```
## 结论
一句话：客户端当前是「作者专用版」还是「可用的参考实现」？

## 问题清单（按分级）
| # | 级别 | 问题 | 位置 | 后果 |
|---|------|------|------|------|
| P0-1 | 阻断 | ... | file:line | 新用户拿不到任何价值 |

## 修复优先级
第一梯队（不修则对外无意义）→ 第二梯队（功能不可信）→ 第三梯队（体验塌陷）→ 第四梯队（可访问性）

## 审查方法说明
- 实测了什么、怎么测的（输入/基线/结果）
- grep 了什么、确认了什么
- 哪些结论是推断、哪些是实机确认
```

## 4. 一次审查的默认动作清单

```bash
# 硬编码扫描
grep -rn "<项目名>\|<宠物名>" src/ main.js panel* --include="*.ts" --include="*.js" --include="*.html" --include="*.css" | grep -v 注释

# 死代码：找无调用者的函数
grep -n "function <名字>" src/ && grep -rn "<名字>(" src/ main.js preload* panel*

# 幽灵功能：data 属性无 CSS 消费者
grep -rn "dataset\." src/ panel.js && grep -rn "\[data-" *.css src/

# 未使用的 IPC 通道（发了没人听 / 听了没人发）
grep -rn "ipcMain\.\|ipcRenderer\." main.js preload*.cjs | 交叉核对

# 文档默认值与代码默认值
grep -n "?? \| \|\| " src/main.ts | grep -E "fps|weight|frames"
```

## 5. 与文档体系的关系

- 本文档是**审查方法**，`07-踩坑实录` 是**踩过的坑**，`10-架构升级评估` 是**架构方向的评估**。
- 审查发现的真实缺陷应回写 `07-踩坑实录`（现象→根因→铁律），让坑成为资产。
- 每次大改动（新增功能/重构/打包配置变更）后跑一遍本清单，比集中大审查成本低得多。
